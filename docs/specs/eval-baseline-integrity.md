# 可信基线与门禁完整性

## Problem Statement
#41 / PR #49 的门禁目前可能把变更后的文档材料当成同版本、把 Trace 缺失误认为低成本，并允许覆盖基线后与自己比较。历史基线包含 75% Schema 合法率、15 题导出成功以及零 Token/成本，不能代表修复后的可信标准。

## Solution
建立可追溯、可校验的数据完整性契约：题集版本覆盖材料正文；普通报告允许降级但门禁和立基线拒绝缺失数据；基线采用受校验的版本化格式，保存指标、有效样本、运行来源及实际可执行容差；立基线与门禁严格互斥。未运行真实模型前，历史文件明确标为待重建并拒绝用于门禁。

## User Stories
1. As a 维护者, I want 修改材料正文就改变题集版本, so that 不会跨材料比较。
2. As a 维护者, I want 相同题集重复运行保持版本不变, so that 重复测量可比较。
3. As a 维护者, I want 缺失 Trace 与真实零用量分开, so that 数据丢失不会被判成成本下降。
4. As a 维护者, I want 不完整结果不能建立基线, so that 基线可信。
5. As a 维护者, I want 基线包含成功率、Schema、导出、页数、需求覆盖、内容分、Token、成本及 P95, so that 回归有量化护栏。
6. As a 维护者, I want 记录幻觉和重试指标但首版不硬拦, so that 口径局限可见。
7. As a 维护者, I want 基线记录来源 run、代码提交、模型及价格配置, so that 变化可追溯。
8. As a 维护者, I want JSON 中的数值容差真正参与比较, so that 修改规则不会只改说明。
9. As a 维护者, I want 立基线和门禁不能同时启用, so that 不会自比较放行。
10. As a 维护者, I want 缺失/无效基线在调用模型之前失败, so that 不浪费额度。
11. As a 维护者, I want 本次只做离线测试并合并代码, so that 不需要 Token。

## Implementation Decisions
- 从最新 main 集成 PR #49 的门禁实现，独立 worktree / codex 分支开发，不动原目录的未提交工作。
- 哈希按稳定排序的题目语义字段和材料原始字节 SHA-256 生成，明确升级题集版本算法。
- 保留普通报告的降级兼容语义；在门禁/基线边界检查逐题 Trace 来源、完整性及有限数值。
- 基线采用版本化 Pydantic 格式；拒绝未知/旧格式、缺必需指标、NaN/Infinity、无有效样本或缺失 Trace 的正式基线。
- 增加页数达成率、需求覆盖率；保存幻觉和重试诊断及样本覆盖率。容差为结构化数值规则。
- 元数据保存报告来源、题集版本、题数、代码提交、模型与价格。历史 DB 报告不伪造运行条件；缺来源信息须明确拒绝正式立基线并提示重跑。
- 三种 CLI 模式互斥，包括环境变量；门禁在真实生成前做基线/版本预检。
- 本次不调用真实 LLM/付费生图，不更新真实测量值；历史基线显式废弃，后续获用户授权才重测立新基线。用户随后明确要求完成代码后提交并合并，本次不做真实评测。

## Testing Decisions
以现有公开边界：题集加载与版本函数、报告到基线转换/读写/比较、评测 CLI 为测试边界；采用临时材料文件、人工构造报告、HTTP/数据库边界替身；先失败再修复。运行相关回归及全量 pytest / Ruff，不运行 make eval。

## Out of Scope
真实模型评测与新测量值、自动接受回退、语义数字换算、视觉 Judge、CI 部署、#42 实现。

## Further Notes
用户明确授权建文档、拆 tickets、实现、提交并合并；明确禁止真实评测且不提供 Token。#41 原 PR 包含在集成提交历史中，不单独合并旧实现。
