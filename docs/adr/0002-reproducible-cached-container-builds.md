# ADR-0002：生产容器的可复现构建与依赖缓存复用

- 状态：已实施；本地检查通过，Linux 容器构建与运行验收待完成
- 日期：2026-10-19
- 范围：后端 Dockerfile、构建上下文、API / Worker 镜像及生产启动命令

SlideForge 在腾讯云 Ubuntu 2 核 4GB 单机上部署，首次安装约 6 分钟。决定采用固定工具版本、锁定依赖、分层构建和 BuildKit 下载缓存，API 与 Worker 共用同一份后端镜像，运行时直接使用镜像内的虚拟环境。目标是减少重复下载，同时保证代码、依赖和发布版本一致；缓存不代替版本锁定。

## 背景与证据

首次构建需要拉取 Python / uv 镜像、下载并安装 Python 依赖、构建项目和获取字体，6 分钟本身不足以说明异常。尚未收集逐阶段耗时，不能据此认定瓶颈，也不承诺后续固定在某个时间内完成。前端打包耗时应与后端构建分开记录。

实施前的仓库存在以下影响构建与运行的行为：

- `backend/Dockerfile` 使用 `python:3.12-slim` 和 `uv:latest`，基础镜像及工具内容可以随时间变化。
- 仅复制 `pyproject.toml` 和 `uv.lock` 后执行 `uv sync`，此时 `app/` 尚不存在；而项目配置了 Hatchling 构建本项目，首次安装存在失败风险。
- 初始依赖同步使用 `--no-dev`，随后下载字体和启动进程却使用普通 `uv run`，可能重新同步依赖并引入开发组。
- 字体下载在 `COPY . .` 之后执行，业务代码变化也会使该层失效；脚本没有显式超时，`|| true` 又会隐藏下载失败。
- 生产 Compose 为 API 和 Worker 分别声明相同构建上下文，未明确用一个发布镜像统一交付。
- `.dockerignore` 已排除 `.env`、`.venv/`、`var/` 和 Python 字节码，但仍可缩小构建上下文。

以上是实施前的代码检查结果；实施和验证进展见文末。

## 决策及理由

### 1. 固定经过验证的版本，升级由发布操作触发

固定 uv 的具体稳定版本；Python 镜像明确 Python 补丁版本和 Debian 发行版，并记录镜像 digest。当前选定 Python `3.12.13-slim-bookworm` 和 uv `0.13.1`，均已从官方镜像仓库查询并固定摘要；uv 已通过本地锁文件检查和两阶段依赖安装，完整 Linux 镜像构建仍待验证。更新镜像时主动更新这些固定值并重新验证，避免长期固定导致安全更新遗漏。

依赖由提交到仓库的 `uv.lock` 决定。构建阶段先检查锁文件与项目配置一致，再以 `--frozen` 安装；项目声明变化而锁文件未更新时应失败，不能在生产构建中静默重新解析依赖。

### 2. 区分两层缓存，分别解决重复安装与重复下载

| 缓存 | 作用 | 失效边界 |
|---|---|---|
| Docker 构建层缓存 | 输入相同时跳过整个依赖安装步骤 | 该步骤的文件输入、指令或上游层发生变化 |
| BuildKit 挂载的 uv 缓存 | 安装步骤需要重跑时，复用已有下载与构建产物 | 缓存被清理、构建器更换，或所需版本 / 平台产物尚不存在 |

在每个需要同步依赖的构建步骤挂载 `/root/.cache/uv`，使用 `UV_LINK_MODE=copy`，使虚拟环境不依赖缓存挂载的持续存在。缓存留在构建器中，不打包进应用镜像。

不从宿主机复制 `.venv`，不把运行容器的虚拟环境作为共享可写卷，不默认使用 `--no-cache`。Linux 镜像的依赖由构建过程生成，不能复用 Windows 的本地虚拟环境。

缓存优先复用符合锁文件和运行平台的产物；缺失时允许下载。不能承诺每次构建完全离线，也不能为了避免下载而继续使用锁文件不匹配的版本。

### 3. 将第三方依赖、字体和业务源码分层

构建顺序确定为：

1. 准备固定版本的 Python 和 uv，设置虚拟环境路径及缓存配置。
2. 复制 `pyproject.toml`、`uv.lock`，检查锁文件一致性。
3. 执行 `uv sync --frozen --no-dev --no-install-project`，缓存第三方运行依赖。
4. 单独复制字体下载脚本及版本清单，获取并验证字体。
5. 复制业务代码、数据库迁移和必需的运行资源。
6. 执行 `uv sync --frozen --no-dev`，完成本项目安装。
7. 设置运行用户和启动命令，交付镜像。

第 6 步仍可能重跑同步，但会复用 uv 缓存；“不重复下载”不等于“永远不执行依赖同步”。普通代码修改不应使第 3 步失效，也不应触发字体重新下载。

字体来源固定到具体版本或提交，并校验 SHA-256；添加显式超时与有限次数重试。默认生产构建要求字体齐全，下载失败则清楚报错并停止构建，删除无条件 `|| true`。产品仍支持缺字时的估算逻辑，但如需发布缺字体的降级镜像，必须通过显式构建参数选择，并在构建输出中标明。

2026-10-19 补充：腾讯云部署实际遇到 GitHub 字体下载多次超时。新增 `SKIP_FONT_DOWNLOAD=true`，直接跳过字体脚本，不产生字体网络请求，立即使用已有估算降级逻辑。原 `ALLOW_MISSING_FONTS=true` 仍代表“尝试下载，失败后允许继续”，两者语义不同；均默认为 false。跳过选项仅影响字体阶段，不清理依赖缓存、不升级依赖、不修改源码锁文件。

### 4. 启动使用已安装环境，不再安装依赖

设置 `PATH=/app/.venv/bin:$PATH`。API 直接运行 `uvicorn`，Worker 直接运行 `arq`，迁移直接运行 `alembic`；字体脚本使用已确定的 Python 路径。同步更新 Dockerfile、Compose 覆盖命令和部署文档，避免只改 API 而遗漏 Worker 或迁移。

容器启动不得访问包索引、修改锁文件或自动安装开发依赖。这里仅约束依赖管理行为；AI 生成、图片服务等业务功能仍需要访问外网。

`--no-dev` 是本次同步操作的选项，不是写入项目的永久开关；该操作生成的运行环境会保存在镜像层中，直接启动程序不会自行增加开发依赖。但后续普通 `uv run` / `uv sync` 仍可能按默认配置装回开发组，因此每个构建同步步骤必须明确使用 `--no-dev`，生产启动和迁移使用虚拟环境里的程序。保留 uv 时可额外设置 `UV_NO_DEV=1` 作为防误操作措施，但不能用它替代构建选项或直接启动约定。

`--no-dev` 仅排除开发依赖组，不会自动判断主依赖是否必要。生产仍安装 `pyproject.toml` 主依赖及其传递依赖，以保留文档解析、认证、生成和导出功能；进一步精简主依赖须先检查实际导入与功能调用，再单独验证，不能仅凭包名删除。

### 5. 一个后端镜像，两个进程角色

API 和 Worker 使用同一镜像引用，区别只有启动命令。每次发布只构建一次，以 Git 提交或明确发布标识打标签，并记录对应 image ID / digest；启动时不再隐式构建第二份镜像。

这样减少重复构建，并保证 API 与 Worker 使用相同代码、依赖和字体。正常启动已有容器不需要重新构建；代码更新才构建新镜像。数据库迁移作为单独发布步骤执行，不能因为容器重启就自动重复跑迁移。

所有长期运行的生产服务使用 `restart: unless-stopped`，Docker 服务设置为开机启动：容器进程退出或服务器重启后自动恢复，用户无需日常手动启动；显式停止的容器保持停止。该策略不监控源码、不自动发布新版本，也不会仅因健康检查失败就重启仍存活的进程。发布新镜像时通过一次 Compose 更新操作重建受影响的 API / Worker 容器，无需用户逐个手动重启进程；涉及数据库迁移时仍按发布顺序单独执行。完整无人值守发布属于后续 CI/CD 范围。

### 6. 缩小上下文并明确运行权限

在现有忽略规则上排除开发测试、评测语料、工具缓存、临时文件和环境备份，例如 `tests/`、`eval/`、`.pytest_cache/`、`.ruff_cache/`、`.env.*`。按实际导入关系检查后再排除，保留 `app/`、`alembic/`、`alembic.ini`、运行脚本及必要资源。密钥仅在运行时注入。

使用固定 UID / GID 的非 root 用户。实施时同步处理 `/data/storage` 及历史数据卷的所有权，确保 API、Worker 都能读写；不能仅添加 `USER` 就认为完成。共享布局目录继续以只读方式挂载。

## 预期行为

| 场景 | 预期行为 |
|---|---|
| 首次构建 / 新服务器 | 下载必要镜像、依赖与字体，耗时最长 |
| 同一构建器、相同输入再次构建 | 大部分步骤命中构建层缓存 |
| 仅修改业务 Python 代码 | 复用第三方依赖与字体层，重新复制代码并安装项目 |
| 修改锁文件中的依赖版本 | 重做依赖安装，复用匹配的 uv 缓存，下载缺失产物 |
| 修改 Python / uv / 基础系统版本 | 上游缓存可能失效，重新构建并验证 |
| 清理缓存 / 换构建器 | 可能重新下载；运行容器和持久化业务数据不应依赖这些缓存 |
| 重启已有 API / Worker 容器 | 不构建、不安装依赖，直接启动进程 |

构建缓存会占用服务器磁盘。60GB 系统盘需要用 `docker system df` 观察占用，按需清理可重建缓存；不将业务数据卷纳入构建缓存清理操作。

## 考虑过的替代方案

- **每次重装或禁用缓存**：实现简单，但重复下载多，受网络影响大；只有诊断缓存问题时按需使用。
- **直接沿用宿主机依赖或运行时安装**：看似节省构建时间，但版本、权限和平台可能漂移，启动依赖网络，放弃。
- **立即实施完整多阶段后端构建**：能进一步隔离构建工具、减少镜像内容，但增加路径、环境复制和权限验证成本；本次先落地分层与缓存，测量体积后再决定是否引入。
- **立即接入镜像仓库与 CI 构建**：长期可减少小服务器构建负担，但需要额外维护凭据和流水线；本次保留单机构建，未来可沿用同一镜像交付约定迁移到 CI。
- **同时重做前端镜像构建**：前端依赖缓存值得单独处理，但不是本次 Python 依赖重复下载的直接原因，本次不扩大范围。

## 实施验收

1. 在部署目标平台完成一次首次构建，分别记录镜像获取、依赖安装、字体获取和总耗时。
2. 不改文件立即再构建，确认第三方依赖层与字体层显示 `CACHED`，记录耗时；不能只根据总耗时推断缓存命中。
3. 仅修改一个业务源码文件再构建，确认依赖层与字体层继续命中缓存。
4. 在临时验证分支更新依赖及锁文件，确认环境版本匹配新锁文件，并观察缓存复用；声明与锁文件不一致时构建应失败。
5. 检查镜像不含生产密钥、宿主机虚拟环境和开发组专属工具；启动 API、Worker、迁移时无依赖同步日志。
6. 验证两种角色使用同一 image ID，非 root 用户能完成共享文件保存、读取和 PPTX 导出。
7. 验证完整流程：迁移、健康检查、文档上传、大纲生成、页面生成、PPTX 导出；字体可用且不触发缺字体估算提示。
8. 主动模拟字体下载失败，确认有明确超时、有限重试和失败状态；只在显式降级模式下允许生成缺字体镜像。
